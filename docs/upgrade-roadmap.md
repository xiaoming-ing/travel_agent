# 旅行 Agent 升级路线图

本文档记录项目后续升级计划。目标不是继续堆叠 Agent 数量，而是把现有系统提升为一个可验证、可解释、可恢复、可扩展的旅行规划系统。

明确不做：Markdown 导出、ICS 日历导出。

## 总体目标

将当前流程：

```text
LLM 调工具 -> LLM 生成行程 -> 用户反馈修改
```

升级为：

```text
需求校验
  -> Agent 采集外部数据
  -> RAG 提供用户资料
  -> 确定性算法生成可行路线
  -> 业务校验与自动修复
  -> 用户多轮调整
  -> 评测与指标记录
```

## 阶段一：修复正确性和输入边界

目标：让非法输入、外部服务失败和 Agent 异常都能稳定处理。

### 任务

- 修复 `backend/app/agents/revise_tools.py` 中 `apply_revision()` 异常分支返回值数量不一致的问题，始终返回 `(plan, tokens, note)`。
- 为 `TripRequest` 增加 Pydantic 校验：
  - `end_date >= start_date`
  - 行程天数限制在合理范围，例如 1-15 天
  - 目的地非空且限制长度
  - 交通方式、住宿类型、偏好使用枚举约束
  - `extra_requirements` 限制最大长度
- 为 `ChatResumeBody`、`KnowledgeUploadBody` 增加长度和格式限制。
- 对过去日期的澄清流程增加日期格式、日期范围和重新计算行程天数的校验。
- SSE 对外只返回通用错误信息，详细异常写入日志。
- 为高德、天气、LLM 失败分别定义可识别的错误类型和降级行为。

### 重点文件

- `backend/app/schemas/request.py`
- `backend/app/api/chat.py`
- `backend/app/api/knowledge.py`
- `backend/app/graph/conversation.py`
- `backend/app/graph/streaming.py`
- `backend/app/agents/revise_tools.py`

### 验收标准

- 直接绕过前端调用 API 时，非法请求返回 422 或明确业务错误。
- 修改 Agent 失败时仍能回到反馈节点，不会因为解包异常结束 SSE。
- 外部 API 失败时返回降级计划，不泄露内部异常堆栈。
- 现有测试全部通过，并新增异常分支测试。

## 阶段二：增加 TripPlan 业务校验层

目标：不把业务正确性完全交给 LLM。

### 任务

新增 `backend/app/agents/plan_validator.py`，在 Phase 2 结构化输出之后执行：

- 起止日期、`trip_days` 和每日日期一致。
- 每日日期连续且从第 1 天开始。
- 每日景点名称必须存在于 `attractions`。
- 景点不能跨天重复，除非明确允许。
- 每天景点数量符合体力约束和用户额外要求。
- 门票、酒店、餐饮、交通预算不能为负数。
- 坐标在合法经纬度范围内，缺失坐标进入地图降级处理。
- 酒店评分和价格格式合法。
- 每日计划引用的酒店和景点数据完整。

校验失败时按以下顺序处理：

1. 使用确定性逻辑修复简单问题，例如日期、重复景点和预算总计。
2. 重新请求一次结构化输出，并在 Prompt 中附带错误列表。
3. 仍失败时返回明确的降级计划和失败原因。

### 验收标准

- 使用固定的非法 JSON 样例测试所有规则。
- 任何进入前端的 `TripPlan` 都通过校验。
- 日志中记录校验失败规则和修复次数。
- 不允许通过修改 Prompt 绕过业务约束。

## 阶段三：完成真实编辑闭环

目标：去除结果页占位交互，让用户能够直接调整行程。

### 任务

- 将结果页的“编辑行程”改为可编辑状态。
- 支持按天编辑景点列表、删除景点、调整景点顺序。
- 支持修改交通方式、住宿类型和单日体力偏好。
- 将编辑操作复用现有 `resume-stream` 流程，避免前后端出现两套修改逻辑。
- 对修改结果进行与阶段二相同的业务校验。
- 删除 `ResultView.vue` 中“功能开发中”的占位 alert。
- 增加加载中、保存失败、修改无效和恢复原方案状态。

### 重点文件

- `frontend/src/views/ResultView.vue`
- `frontend/src/views/ChatView.vue`
- `frontend/src/components/trip/DailyPlan.vue`
- `backend/app/api/chat.py`
- `backend/app/agents/revise_tools.py`

### 验收标准

- 用户可以在结果页修改某一天的景点并看到地图、每日计划同步更新。
- 修改失败时原方案不丢失。
- 刷新页面后仍能从 checkpoint 恢复最新方案。
- 移动端不依赖 hover 完成编辑。

## 阶段四：加入确定性路线优化

目标：将项目核心能力从“LLM 排行程”升级为“LLM 理解需求 + 算法生成可行路线”。

### 推荐实现顺序

1. 为景点补充标准化字段：营业时间、游览时长、门票、经纬度、室内/室外、体力等级。
2. 获取景点之间的距离或预计交通时间，优先使用地图服务，失败时使用 haversine 距离估算。
3. 根据地理位置进行景点聚类，减少跨区域移动。
4. 按每天可用时间、每日最大景点数和体力限制分配景点。
5. 在每天内部按距离、营业时间和用户偏好排序。
6. 对必去景点、预算上限和用户指定景点提供硬约束。
7. 最后由 LLM 生成自然语言描述，而不是让 LLM 决定最终可行性。

### 第一版可以使用的启发式算法

- 先固定用户指定的必去景点。
- 按经纬度对剩余景点做简单聚类。
- 每天选择一个区域，按最近邻排序。
- 超过每日时间预算时移除低优先级景点。
- 对不满足条件的方案返回具体冲突原因。

后续再评估 OR-Tools、Google Routes API 或其他路线求解器。

### 验收标准

- 输出每个景点的选择原因和每一天的路线成本。
- 方案不违反营业时间、每日时长和景点重复约束。
- 至少准备 20 条固定需求，比较优化前后的重复率、超时率和跨区移动距离。
- LLM 失败时，仍能使用确定性逻辑生成最小可行路线。

## 阶段五：增强 RAG 可信度

目标：让知识库从“文本注入”升级为“可追溯的景点资料检索”。

### 任务

- 为 chunk 增加景点名、来源、章节、上传批次和创建时间 metadata。
- 检索结果返回来源和引用编号。
- 将景点名的字面匹配与向量相似度组合为混合检索。
- 对用户资料按 `user_id + city` 做严格隔离。
- Prompt 中明确标记资料为不可信外部内容，防止资料中的指令影响系统行为。
- 前端展示描述的资料来源和引用内容。
- 当资料没有命中时，明确区分“无资料”和“检索失败”。

### 规模升级路径

当前 SQLite 全量读取城市 chunk 适合小数据量。数据量增大后再迁移到 FAISS、Qdrant 或 PostgreSQL + pgvector，并保留同一套 Retriever 接口。

### 验收标准

- 检索结果能定位到具体来源。
- 构造同义表达、景点名直命中和无关资料样例，验证混合检索效果。
- 测试不同用户不能检索到彼此的资料。
- 记录 Recall@K、命中率和无资料误命中率。

## 阶段六：Agent 评测和可观测性

目标：用数据证明系统确实变好了。

### 评测集

至少覆盖：

- 日期错误和偏好缺失
- 预算有限
- 带老人或小孩、要求少走路
- 用户指定具体景点
- 更换某一天景点
- 更换酒店档次
- 天气或高德接口不可用
- RAG 有命中、无命中和恶意指令资料
- LLM 结构化输出失败

### 指标

- 工具调用正确率
- 结构化输出通过率
- TripPlan 业务校验通过率
- 景点跨天重复率
- 每日路线超时率
- 修改成功率
- 平均响应耗时和 P95 耗时
- 平均 Token 消耗和单次规划成本
- RAG Recall@K 和引用准确率

### 实现建议

- 用 mock provider 替代真实高德、天气和 LLM，保证测试可重复。
- 增加工作流级集成测试，不只测试单个函数。
- 使用结构化日志记录 `request_id`、`thread_id`、`user_id`、阶段名、耗时和 token 数。
- 保留失败输入、失败节点和修复结果，方便复盘。

## 阶段七：生产化改造

目标：明确单机版本的边界，并完成可扩展部署方案。

### 任务

- 生产环境强制要求 `JWT_SECRET`、LLM Key 和地图 Key，不使用默认 secret。
- 将 Token 配额改为数据库原子扣减，避免并发超额。
- 使用 `httpx.AsyncClient`，统一外部请求超时、重试、退避和连接复用。
- 为高德和天气增加短期缓存，降低重复调用和延迟。
- 增加 Provider 抽象，便于替换高德、天气或 LLM 供应商。
- SQLite checkpoint 迁移到 PostgreSQL，Redis 用于限流和配额热点数据。
- 增加 Docker Compose、数据库迁移和 CI 流程。
- 增加健康检查、依赖检查和基础 metrics。

### 验收标准

- 外部服务超时不会阻塞整个请求到无期限。
- 多个并发请求下配额不会超过上限。
- 应用可通过 Docker Compose 一键启动。
- CI 至少执行后端测试、类型检查和前端构建。

## 推荐实施顺序

```text
阶段一 正确性边界
  -> 阶段二 业务校验
  -> 阶段三 编辑闭环
  -> 阶段四 路线优化
  -> 阶段五 RAG 可信度
  -> 阶段六 评测与观测
  -> 阶段七 生产化
```

如果时间有限，优先完成阶段一、二、四、六。这四个阶段最能提升项目的技术含量和简历可信度。

## 完成后的简历主线

```text
设计并实现基于 LangGraph 的可恢复多轮旅行规划系统，结合外部实时数据、用户偏好 RAG 和确定性路线优化，生成满足日期、距离、预算和体力约束的结构化行程；通过业务校验、故障降级和 Agent 评测体系提升输出可靠性，并使用 SSE、checkpoint、JWT 和配额控制支持完整的多用户交互流程。
```

简历中的指标只填写实际评测结果，不要预先编造提升比例。
