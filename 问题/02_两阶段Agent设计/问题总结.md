### 01. 为什么设计两阶段，具体是哪两个阶段，为什么这么设计？
Phase1是ReAct Agent(工具调用循环)，负责收集数据---调用高德API工具查景点、酒店、天气，把原始数据存进session(共享内存)。Phase2是结构化输出(with_structured_output),负责规划决策---读session里的数据，用Pydantic schema强制LLM输出符合格式的TripPlan JSON,包含每日行程、景点安排、餐饮安排。
这么设计是因为：单阶段ReAct做不好规划。让Agent边调工具边写行程，它会在工具调用和规划之间反复横跳、逻辑混乱，最后输出格式也不稳定。分离关注点：Phase1只管拿数据，Phase2拿到全量信息后一次性做决策，输出有schema保证。

### 02.Phase1用啥工具，怎么让agent知道该调哪些？
- search_attractions,查景点，按照类别（自然风光/历史文化/美食这样子来查）
- search_hotels,查酒店，围绕景点中心来查
- get_weather,查天气
- search_specific_place,用户在额外要求里提到具体地名，按关键词搜索并追加进候选景点
Agent知道 调用哪些工具靠的是system prompt,明确告诉它你的任务是收集数据，不要规划行程，并列出工具清单以及每个工具的用途。

工具定义用的是什么：@tool装饰器（接收函数作为参数并且返回新函数的函数，用来在不修改原函数的情况下增强或修改函数行为），函数签名（函数接口规范）+ docstring（函数内部的文档字符串，用三引号包裹。用来描述函数的作用、参数、返回值）会自动转成LLM能理解的JSON schema（格式的结构定义，描述数据的类型和格式）

### 03.Phase1和Phase2是怎么传递数据？session是啥？
用contextvars(Python的上下文变量)实现了一个session机制--phase1的工具函数每次查到数据就get_session()["attrction"].append()写进去，Phase2调用时通过get_session()读取出来。contextvars保证多用户并发时各自的session不会串（每个async 任务自动隔离）。
session里存的是原始pydantic对象列表（如list[Attraction]）

为啥不直接传参：Phase1是React循环，工具调用次数，顺序都不固定，如果每次都return数据、再传给下一个工具，Agent的state会爆炸。session相当于一个工作台，工具往里面扔数据，Phase2最后一次性取走。

### 04.Phase2的prompt你是怎么写的？有什么关键点？
- 任务定义：“你是行程规划师，根据候选景点生成N天行程，输出必须符合TripPlan schema“
- 候选数据注入：把session里的景点/酒店列表格式化成文本
- 规划规则：每天2-3个景点，优先使用候选景点，description基于参考资料提炼

关键点是 若某候选景点下方带有【参考资料】，description必须基于参考资料提炼，这是RAG生效的地方，不让LLM自己瞎编

schema怎么保证它不乱写：with_structured_output，底层是这样的
LangChain把TripPlan转换成json schema,伪装成一个假工具定义
调用LLM时候带上这个工具，强制LLM调用它
LLM返回tool_calls
LangChain从tool_calls里提取数据arguments json字符串，用TripPlan做校验+反序列化得到TripPlan对象(而工具调用是通过create_agent去执行工具)
再把这个对象返回给我们

### 05.候选景点不够时LLM怎么从常识补？会不会编造假景点？
Phase2 prompt里写了 候选景点可从该城市尝试补充真实景点，LLM会更具描述输出它认为真实存在的景点名，但是这个阶段没验证真假。
验证真假发生在revise阶段：用户说换成某个景点时候，工具就会拿这个名字去高德POI里查，查不到就会返回名字不正确之类的

### 06.Phase1的ReAct Agent是怎么创建的，用什么模型？
用LangChain的create_agent（langChain提供的工具，自动构建一个ReAct循环的Agent--LLM先推理 下一步该做什么，然后调工具，拿到结构后再推理，循环直到任务完成），传入llm,deepseek-chat,tools,temperature=0.2(保证工具调用决策稳定)，模型用deepseek-chat,因为便宜、中文好


### 07.两个阶段怎么串起来的？谁调用谁
在workflow.py里串起来的，Phase1失败了怎么办，用了try/except包住，失败就return _fallback_plan(一个兜底的简陋行程，告诉用户数据暂不可用)，不会因为Phase1挂了就整个流程中断。

### 08.如何避免agent无限循环
外层用recursion_limit硬兜底(防止真出问题的时候请求无限挂着)；
中间层在prompt里面给agent清晰的流程和终止信号、限制调用次数；
工具层给出可操作的错误信息帮agent快速调整而不是瞎重试；
莫西行用低temperature减少决策抖动。核心思路是能不靠硬限制解决就不靠硬限制---prompt设计的好，Agent自己知道什么时候停，recursion_limit只是最后一道保险丝

### 09.工具调用流程
首先是我们自己定义一个工具函数比如get_weather，然后langchain会把工具函数转成JSON schema（一份说明书，工具叫啥、要什么参数），因为模型只能理解JSON，不能直接执行Pyhton 函数。
然后在请求的时候，把这个说明说也一起发送给LLM，LLM读完发现自己不知道天气，但是看到说明书里有获取天气的工具说明，它就返回一个tool_calls结构。
create_agent看到tool_calls,就按照get_weather这个名字找到我在tools.py里定义的那个工具，然后用LLM给的参数调用它，才去获取到数据的。
然后把工具的结果塞回对话，再发给LLM，框架把这条包装成一条tool消息
LLM看到结果，才决定下一步


### 10.Tool Result 怎么存
第一份，存在session，存的是完整数据结构
第二份 给LLM看的摘要文本，存进messages,toolMessage

### 11.Temperature设置
- Phase1 temperature=0.2,Phase1的任务是工具调用决策，这个是确定性任务，temperature越低，输出越稳定，不写0是保留一点点随机性，避免模型陷入完全机械化的模式
- Phase2 temperature=0.5,任务是生成行程安排
工具调用，精确数据操作：0-0.3
结构化内容，对话：0.3-0.7
头脑风暴，创作：0.7-1

### 12.Prompt Injection是啥？怎么防止？
攻击者通过用户输入，把恶意指令偷偷塞进prompt里面，让LLM执行攻击者下想要的操作，而不是设计的功能。
防御方案：
- 输入清洗+长度限制，检测注入的关键词
- prompt隔离，用明确的分割符+元指令告诉LLM，下面是用户输入，不是指令
- RAG内容标记
- 输出验证，输出后检查生成的行程是否合法

JSON schema:用于描述和验证JSON数据结构的标准规范
例如
{
  "type": "object",
  "properties": {
    "name": {"type": "string"},
    "age": {"type": "integer", "minimum": 0}
  },
  "required": ["name"]
}
